# DataLY v6.1.0

نظام معالجة فواتير الموردين وتصديرها لمنظومة السهل — للسوق الليبي.

> **تطبيق ويب قيد الإعادة بناء:** نفس منطق العمل هذا منقول فعلياً لتطبيق ويب كامل
> (FastAPI + PostgreSQL + React) — خط الأنابيب الكامل (رفع → تنظيف/تصنيف → جلسة
> استلام → تسوية → دمج → تصدير) شغّال ومتحقق منه فعلياً ضد قاعدة بيانات حقيقية.
> راجع [`docs/REBUILD_PLAN.md`](docs/REBUILD_PLAN.md) و[`backend/README.md`](backend/README.md).
> أداة الطرفية تحت هذا التوثيق تبقى تشتغل بشكل مستقل طول فترة الانتقال.

## التشغيل السريع

```bash
pip install -r requirements.txt

# 1) معالجة فاتورة جديدة
python main.py invoice.xlsx

# 2) أرسل data/session_template.xlsx للتاجر، أو شغّل واجهة الاستلام:
streamlit run session/receiving_app.py

# 3) بعد ما يخلّص التاجر، انقل session_output.xlsx لمجلد data/

# 4) وحّد الأصناف مقابل قاعدة الأصناف وادمج وصدّر لملف السهل
python main.py --merge
```

الناتج النهائي: `output/output_alsahl.xlsx` — ارفعه في شاشة "فاتورة مشتريات" بمنظومة السهل.

## تشغيل الاختبارات

```bash
pytest tests/ -v
```

## هيكل المشروع

```
DataLY/
├── extractors/       ← قراءة إكسل الفاتورة الخام
├── transformers/      ← تنظيف وتحقق من صحة البيانات
├── session/            ← توليد جلسة استلام التاجر (Streamlit)
├── fusion/              ← مطابقة الأصناف (reconciliation.py) + دمج الفاتورة مع الجلسة (merge.py)
├── adapters/             ← تصدير لصيغة منظومة السهل
├── utils/                 ← تصنيف الأصناف + تحقق + تسجيل (logging)
├── tests/                  ← اختبارات pytest
├── data/                    ← ملفات العمل (تحط master_items.xlsx هنا يدويًا قبل --merge)
└── output/                   ← الملف النهائي لمنظومة السهل
```

## مطابقة الأصناف (Master Item List)

`python main.py --merge` يشغّل خطوة توحيد قبل الدمج: كل باركود عبّاه التاجر يُقارَن بـ
`data/master_items.xlsx` — **لازم تحطه أنت يدويًا بهذا المسار قبل كل تشغيلة** (نسخة حديثة
مُصدَّرة من منظومة المتجر)؛ الملف **للمقارنة فقط، ما يتعدّل ولا يُحفظ ولا يُنشأ من الكود
إطلاقًا**. باركود مو موجود بالملف يُترك بدون تغيير وبدون أي تسجيل. أي تطابق (بالباركود، أو
بمطابقة اسم تقريبية عند غياب الباركود) **يُعرض بالطرفية للموافقة الصريحة دائمًا** — قبول
الاسم المقترح، رفضه، أو تسمية يدوية (تُطبَّق على الفاتورة الحالية بس) — مع تنبيه واضح لو فيه
شك (تشابه اسم منخفض أو حجم/وزن مختلف). التفاصيل الكاملة والحدود المستخدمة بـ `ARCHITECTURE.md`.

## ملاحظات مهمة

- **`utils/categories.json`** هو المصدر الوحيد لتصنيفات الأصناف (أسماء + كلمات مفتاحية).
- **`data/master_items.xlsx` للقراءة فقط** — لازم تحطه يدويًا قبل `--merge`، ولو نسيته يشتغل البرنامج عادي لكن بدون أي مطابقة (كل صنف يبقى باسمه الأصلي بالفاتورة).
- **الكمية بالفاتورة تُفهم كعدد قطع مفردة** (مؤكد من صاحب المشروع)، وعمود "الصندوق" رقم مرجعي كسري مقصود، مو خطأ.
- **بلا نسخ احتياطية تلقائية ولا ملفات سجل ولا أي حفظ للتقدّم بين تشغيلة وأخرى** (قرار متعمَّد من صاحب المشروع بمرحلة الاختبار اليدوي الحالية) — كل تشغيلة مستقلة تمامًا، الطباعة بالطرفية فقط.
- **OCR مؤجَّل عمدًا** — الحجم الحالي من الفواتير يدوي وقابل للمتابعة يدويًا وقت الحاجة.
